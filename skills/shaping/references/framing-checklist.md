# Framing Checklist

Framing closes why this problem is worth shaping.

Ask questions one at a time. Do not dump the whole checklist into the chat.

When asking a question:

- Include your recommended answer when you can.
- If repo docs or code can answer it, inspect them instead of asking.
- Use concrete scenarios when the user's language is vague or overloaded.

## Close These

- Problem: what is actually wrong?
- Current alternative: how is it handled now?
- Baseline: where does the current way break?
- Desired outcome: what state changes after this work?
- Success criteria: how will we know it improved?
- Appetite: what time and scope boundary should shape the solution?

## Framing Checkpoint

Use this as a lightweight checkpoint, not a ceremony. It is fine to move into shaping and come back if the solution work exposes a weak frame.

The frame is probably strong enough when:

- The need is explainable in one or two sentences.
- The current alternative is visible.
- The baseline is concrete.
- Desired outcome is a state change, not just a feature name.
- There is a success criterion.
- There is a reason users will act now.
- First use is visible even from an empty state.
- The original feature request has been narrowed to the actual breaking point.
- Appetite acts as a constraint on the solution.

This checkpoint means the problem is clear enough to shape. It is not build approval and not solution approval.

## Return To Framing

Return here if later steps reveal that problem, baseline, desired outcome, or appetite is unstable.
