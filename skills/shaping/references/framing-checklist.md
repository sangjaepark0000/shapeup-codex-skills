# Framing Checklist

Framing은 이 problem을 shaping할 가치가 있는 이유를 닫는다.

checklist 전체를 chat에 던지지 않는다.

## Close These

- Problem: 실제로 무엇이 잘못되어 있는가?
- Current alternative: 지금은 어떻게 처리하고 있는가?
- Baseline: 현재 방식은 어디서 깨지는가?
- Desired outcome: 이 작업 뒤 어떤 상태가 달라지는가?
- Success criteria: 나아졌다는 것을 어떻게 알 수 있는가?
- Appetite: 어떤 시간과 scope boundary가 solution을 제약해야 하는가?

## Framing Checkpoint

ceremony가 아니라 가벼운 checkpoint로 사용한다. solution 작업이 weak frame을 드러내면 shaping으로 갔다가 돌아와도 된다.

frame은 대체로 다음 상태면 충분히 강하다.

- need를 한두 문장으로 설명할 수 있다.
- current alternative가 보인다.
- baseline이 concrete하다.
- desired outcome이 feature name이 아니라 state change다.
- success criterion이 있다.
- 사용자가 지금 움직일 이유가 있다.
- empty state에서도 first use가 보인다.
- original feature request가 실제 breaking point로 좁혀졌다.
- appetite가 solution의 제약으로 작동한다.

이 checkpoint는 problem이 shape할 만큼 명확하다는 뜻이다. build approval도 solution approval도 아니다.
